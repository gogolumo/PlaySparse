# Release preparation and updater gate

Ordinary push/PR jobs retain unsigned app/DMG, NSIS, deb and AppImage builds. Optional signing runs only for a manually dispatched workflow on `main` with the complete relevant secret set. Signing failures fail the build; they do not relabel an unsigned result as signed. No certificates/keys are stored in this repository. Signed release execution remains NOT VERIFIED until real credentials and platform acceptance are available.

macOS GitHub Secrets: `APPLE_CERTIFICATE` (base64 Developer ID Application p12), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD` (app-specific password), `APPLE_TEAM_ID`. Tauri imports the certificate, signs the app/sidecar with hardened runtime, submits notarization and staples the app. CI verifies code signatures and the app staple before creating the headless DMG. The enclosing custom DMG is a transport for the stapled app; DMG-specific notarization/stapling is not configured. Do not advertise a separately notarized DMG. See [Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/) and [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

Windows Secrets: `WINDOWS_CERTIFICATE` (base64 Authenticode pfx), `WINDOWS_CERTIFICATE_PASSWORD`. CI imports into the current-user certificate store, emits a temporary Tauri thumbprint/SHA256/timestamp config, builds/signs NSIS, verifies the installer signature and removes the certificate/pfx/config in `finally`. Token/HSM/EV certificates may require a custom signing service rather than exportable pfx. See [Tauri Windows signing](https://v2.tauri.app/distribute/sign/windows/). Real certificate execution and SmartScreen behaviour remain NOT VERIFIED.

Linux retains Tauri category/description/package metadata. SHA256SUMS covers final distributable packages after macOS tar creation. Checksums are integrity metadata, not an authenticated release signature. Package signing and repository publication are separate future gates. Download artifacts only from a trusted workflow/commit.

## Updater architecture (disabled)

No updater plugin, updater endpoints, keys or automatic installation are enabled. Future integration needs an independently managed Tauri updater signing key/public-key pin, HTTPS endpoints with version/platform/architecture-specific artifacts, manifest signatures, OS-signed/notarized installers, authenticated publication and a tested key rotation/rollback policy. Never reuse Authenticode/Developer ID secrets as an updater key or place private updater keys in the frontend. Tauri updater artifact signatures are separate from OS signing: [official updater documentation](https://v2.tauri.app/plugin/updater/).

The backend must refuse installation while any storage job or runtime session is active, require user confirmation, stage downloads separately, preserve/reconcile the versioned library/backup and verify signatures before running installers. Test offline/download interruption, bad signatures, downgrade policy, schema migration and restart recovery on physical machines before enabling production updates. No update may terminate games or force-unmount to satisfy an installer.
